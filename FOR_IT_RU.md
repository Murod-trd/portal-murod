# Передача Toshkent Invest в ИТ — 0.3.0-rc.12

> Начните с [server-handoff/handout.md](server-handoff/handout.md): единый документ передачи, установки и приёмки релиза **0.3.0-rc.13**. Результаты проверок ниже относятся к rc.12.

Дата: 03.11.2026. По последнему решению владельца полную штатную установку/приёмку на Linux выполняет ИТ-служба. Это исходники Python backend/worker, статический frontend, миграции и установочные инструменты, а не уже развёрнутый корпоративный сервер и не офлайн-набор контейнеров.

Локально подтверждены: 299 тестов на PostgreSQL без пропусков; TypeScript/ESLint/component/build; Ruff/Bandit High/Medium=0, Django/migrations/OpenAPI/types; base/prepared/final security gate без High/Critical; настоящий HTTPS трёх ролей, ClamAV/OCR/публикация/поиск; зашифрованное восстановление в отдельные тома. Полные границы и датированные доказательства: [статус](docs/RC12_TECHNICAL_STATUS_RU.md), [сводка](docs/verification/2026-11-03-rc12-summary.json). Три Medium одноразового npm builder остаются видимыми. Это не независимый пентест.

## Согласованный вход

Индивидуальные логин/пароль без обязательной смены на первом входе и без аутентификатора. Стандартные параметры: REQUIRE_MFA=none, REQUIRE_PASSWORD_CHANGE=false, SESSION_TTL_SECONDS=43200, SESSION_IDLE_SECONDS=43200. Настройка существующей установки сохраняется; для перехода со старой политики ИТ задаёт эти параметры явно. [Решение владельца](docs/adr/003-password-login-and-three-ui-languages.md).

## Что передаёт разработчик

| Каталог/файл | Назначение |
|---|---|
| apps/web/ | Статический React/TypeScript frontend: сотрудники, структура, новости, документы, профиль, HR/admin, RU/UZ/EN |
| backend/ | Python/Django/DRF API и worker, серверные права, сессии/CSRF/MFA, миграции, OCR/карантин и тесты |
| operations/, portalctl | Установка, диагностика, обновление, копии, восстановление и приёмка |
| deploy/, Dockerfile, compose.yaml | Описание стандартного Linux-стенда; immutable bases и hash-lock инструментов |
| requirements*.lock, package*.json | Зафиксированные зависимости; Python hashes и npm integrity |
| docs/, HANDOVER_RU.md, RUN_ACCEPTANCE_RU.md | Требования, архитектура, эксплуатация, границы доказательств и последующая приёмка |
| frontend-dist/ | Входит только в архив с --include-frontend после новой успешной сборки; содержит BUILD-PROVENANCE.json |
| RELEASE-MANIFEST.json | Создаётся упаковщиком из чистого окончательного коммита; хеши включённых исходников/артефактов |

Ни секреты, ни данные компании, ни `.deploy`, venv/node_modules, cookies/TOTP и закрытые логи в архив не входят. Установочные параметры создаются ИТ на сервере. Manifest сформирован штатным упаковщиком из коммита текущей поставки; после изменения исходников его необходимо пересоздать, не отключать проверку.

## Ответственность ИТ

Предоставить отдельный Linux x86_64 сервер/VM: Python 3.10+, OpenSSL, Docker Engine/Compose 2.24+, 4 vCPU, минимум 12 ГиБ RAM и 40 ГиБ свободного места (предпочтительно 16 ГиБ RAM). Подготовить внутреннее DNS-имя, частный адрес, офисные/VPN CIDR, TLS-цепочку/ключ, место копий и отдельное хранение recovery-ключа. Доступ извне — через корпоративный VPN. Реальные параметры в код не зашиты.

На сервере приложения Node/npm API не запускаются. Стандартная поставка использует PostgreSQL, Python API/worker, ClamAV, Nginx TLS и закрытый файловый том. S3 необязателен. БД/AV/worker не публикуются в интернет. Одна VM остаётся единой точкой отказа.

## Порядок подключения

1. Сверить SHA-256 архива и manifest после извлечения, сохранить исходную поставку. Не распаковывать поверх изменённой установки.
2. На отдельном Linux x86_64 стенде выполнить [RUN_ACCEPTANCE_RU.md](RUN_ACCEPTANCE_RU.md); затем ручную браузерную матрицу [BROWSER_ACCEPTANCE_RU.md](docs/BROWSER_ACCEPTANCE_RU.md). Windows-прогон общей команды остановлен до установки host guard; отдельные перечисленные контейнерные проверки выполнены.
3. В постоянном каталоге задать реальные параметры компании и установить по [HANDOVER_RU.md](HANDOVER_RU.md). Синтетические аккаунты, сертификаты и данные разработчика не поставляются.
4. Проверить офис/VPN/TLS/ACL, приёмку реальных сканов, оповещения, копии и восстановление на другом физическом сервере. Утвердить RPO/RTO и эксплуатационный допуск до реальных данных.

PostgreSQL — 17.12 (пакет 17.11-r0 удалён из Alpine 3.24; минорное обновление в той же линии хранения), но использует signed-APK storage family `postgresql17-apk-alpine3.24`. Прежние upstream/Debian/Alpine PGDATA не подключать к новой сборке: только отдельный логический перенос по [POSTGRES_MIGRATION_RU.md](docs/POSTGRES_MIGRATION_RU.md). Автоматический update/restore запрещает несовместимое семейство; manifest копий не редактировать для обхода.

`technicalChecksPassed` полной Linux-команды здесь не заявлен. `productionApproved=false` сохраняется до внешнего допуска. Независимый пентест, DNS/TLS/VPN компании, целевая нагрузка, реальный OCR-корпус и второй физический recovery-хост локальными тестами не подтверждены.
