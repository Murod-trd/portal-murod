# Установка на сервер ИТ

Короткая передача — [HANDOVER_RU.md](../HANDOVER_RU.md). Поддерживаемый профиль: выделенная Linux x86_64 система/VM, стандартный локальный Docker Engine `/var/run/docker.sock`, Compose v2.24+, Python 3.10+ на хосте. Приложение в контейнере использует Python 3.12. На Windows Server выделяется Linux VM. Docker на неизвестном действующем сервере установщик не переустанавливает и не перенастраивает.

ОС исходного сервера заказчику неизвестна. Поэтому «подключение к любому серверу без проверки» не обещается. `python3 portalctl inspect-host` выдаёт безопасную сводку; для Windows есть `operations/Inspect-Server.ps1`. Требуются 4 vCPU/12 ГиБ RAM минимум, желательно 16 ГиБ, 40 ГиБ свободного места плюс отдельное место под копии. Это консервативные требования установщика, не результаты нагрузочного теста 150 одновременных пользователей.

## Один раз перед установкой

ИТ задаёт внутреннее имя/DNS, частный IPv4 адрес сервера, офисные/VPN CIDR, действительный сертификат/ключ и каталог копий вне каталога релиза. Внешний доступ — только VPN. Подключение DNS/VPN/доверия к CA на клиентах выполняет владелец сети; код портала не заменяет сетевую инфраструктуру.

Из постоянного каталога релиза:

```bash
sudo python3 portalctl configure --origin https://portal.company.internal \
  --bind 10.20.0.10 --allow 10.20.0.0/16 --allow 10.8.0.0/24 \
  --tls-cert /secure/fullchain.pem --tls-key /secure/privkey.pem \
  --ca-file /secure/company-root-ca.pem \
  --backup-dir /mnt/backup/toshkent-portal
sudo python3 portalctl doctor
sudo python3 portalctl install --admin-login individual.admin --admin-name 'ФИО администратора'
sudo python3 portalctl schedule --enable
```

Адреса — примеры, не реальные параметры компании. `--ca-file` опционален, если цепочка уже доверяется ОС. Генерируются независимые секреты, приватный recovery key, закрытый env, Nginx ACL и конфигурация. Проверяется соответствие сертификата имени/ключу и запас срока не менее недели. Повторная configure сохраняет существующие секреты и возвращает отказ вместо перезаписи. Настройка создаётся атомарно.

Первый пароль администратора вводится скрыто и затем меняется пользователем при первом входе; MFA обязательно. Автоматизация может применять `--password-stdin`, но не пароль в аргументах/логах. Уже созданный администратор при повторе незавершённой установки сохраняется.

## Что запускает install

Проверка целостности RELEASE-MANIFEST, архитектуры/ресурсов/Docker/Compose/адреса → pull закреплённых образов → сборка API/worker → PostgreSQL/ClamAV → миграции отдельной ролью → API/worker/HTTPS → техническая и внешняя HTTPS-проверки → настоящий чистый файл, EICAR и OCR через очередь → первая AES-GCM копия с проверкой её аутентичности → повторная готовность. При ошибке внешняя точка входа останавливается; успех не печатается. Повтор install поверх завершённого развёртывания запрещён: используется update.

В запущенных API/worker-образах Node нет. Файлы — в закрытом томе `private-files`; только API имеет к нему доступ. Nginx/worker том не монтируют. PostgreSQL доступен только по внутренней сети, runtime portal_app имеет DML без DDL/CREATEDB/CREATEROLE/SUPERUSER, миграции выполняет portal_owner. БД и антивирус не публикуют host-порты. У API нет внешнего egress; ClamAV отдельно получает обновления сигнатур.

Первый запуск требует внешних источников образов/зависимостей/сигнатур либо подготовленных корпоративных зеркал. Это исходный установочный комплект, не офлайн-архив уже собранных контейнеров. Нельзя отключать AV/проверку TLS для обхода недоступного источника.

## Проверка на месте

```bash
sudo python3 portalctl check --pipeline --files
sudo python3 portalctl status
```

Отчёт — `.deploy/last-check.json`. Он не содержит паролей или персональных имён. `backupFresh` требует недавнюю аутентифицированную копию с существующими файлами. Полный тест worker создаёт только временный неопубликованный документ/служебные файлы, затем блокирует и ставит их на удаление. Обычные новости сотрудников он не публикует. Шаблон `container-release-acceptance` в GitHub Actions отдельно запускает установку и восстановление на runner достаточной мощности; здесь этот workflow не выполнялся.

HTTPS-проверка использует нормальное доверие к сертификату, не следует редиректам и не использует ambient HTTP proxy. Офис/VPN адрес должен соответствовать ACL. При loopback-проверке Docker может представить адрес своего bridge: разрешать только нужный адрес администрирования, не открывать весь интернет.

## Дополнительные проверки 0.3.0-rc.3

До production-допуска изучить docs/SECURITY_ACCEPTANCE.md: скан базовых PostgreSQL/Python/Node образов содержит High/Critical. Workflow release-acceptance сканирует также конечные образы и блокирует строгий gate при таких находках. Это не отключает техническую диагностику и не выдаёт разрешение на эксплуатацию.

PostgreSQL `pg_trgm` создаётся администратором до миграций; runtime portal_app остаётся без DDL. Обновление существующего экземпляра также обеспечивает наличие расширения. Снимки pg_dump 17 исключают сам объект инфраструктурного расширения (`--exclude-extension=pg_trgm`); оно должно быть установлено на принимающем стенде до pg_restore. Индексы/данные портала входят в копию. Этот путь требует нативного прогона.

Для второго экземпляра в приёмке есть `configure --project-name portal-recovery-acceptance` с отдельными рабочим каталогом, HTTPS-портом, секретами и томами. Имя проверяется, а метки владения сохраняются. Workflow сравнивает контрольные суммы стабильных бизнес-записей до/после восстановления и проверяет реальные файлы и pipeline. Два Compose project на одном runner не являются проверкой другого физического сервера.

В rc.4 Python и одноразовый Node-сборщик используют Debian trixie; PostgreSQL остаётся bookworm. Переход требует реальной повторной сборки/приёмки контейнеров. Добавлен инструментальный том backup-work; итоговая конфигурация проверена официальным Compose parser также с профилем tools. Сам контейнерный запуск здесь не выполнен.
