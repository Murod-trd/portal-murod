Редакция требований: 01.11.2026, Asia/Tashkent; дополнена требованиями безопасности по запросу заказчика. Основание: исходный мастер-промпт, прототип v3 и последующее интервью с заказчиком.

## 0. Задача исполнителя и порядок приоритетов

Ты — ведущий full-stack инженер и UX/UI-разработчик корпоративных приложений. Реализуй работающий внутренний портал АО «Компания Ташкент Инвест», а не ещё один HTML-макет. Работай в отдельном репозитории портала. Не изменяй Glorix и другие проекты.

Три обязательных сценария первого запуска имеют одинаковый продуктовый приоритет:

1. Найти коллегу по ФИО, должности, офису, внутреннему/мобильному номеру или доступной части даты рождения; увидеть контакты и руководителя.

Это информационный интранет, справочник и библиотека документов. Не добавляй ERP, бухгалтерию, CRM, кадровый расчёт, микросервисы, Kafka или AI-чатбот. OCR нужен для поиска по документам, а не для создания официальных текстов.

**Этот файл заменяет предыдущую редакцию мастер-промпта целиком.** Старый README и код v3 — справочный материал о прототипе, а не источник более приоритетных правил. Не восстанавливай из старого задания роли CONTENT_EDITOR/SYSTEM_ADMIN с прежними ограничениями, обязательный корпоративный SSO, закрытые группы документов, обязательное двуязычное заполнение и номер рабочего места.

Перед изменениями прочитай README, docs, миграции и имеющийся код. Переиспользуй рабочие решения; не создавай параллельные реализации. После значимых изменений обновляй CHANGELOG и документацию. Не спрашивай заново о решениях, явно записанных ниже. Для ещё неизвестных внешних параметров используй конфигурацию и документированные заглушки без реальных секретов.

После краткого аудита переходи к изменениям кода, миграциям, запуску и тестам. Не объявляй портал готовым по скриншоту, написанным тестам или скрытым кнопкам. Всегда различай «написано», «запущено», «проверено» и «не проверено».

## 2. Масштаб, размещение и сопровождение

- Около **150 пользователей** при первом запуске; несколько офисов/зданий.
- Первоначально **несколько десятков документов**. Система должна сохранять работоспособность при росте без обещаний производительности, не подкреплённых измерением.
- В офисе — доступ из внутренней сети; извне — **только через корпоративный VPN**. Логин и пароль требуются в обоих случаях.
- Наличие готового VPN пока неизвестно: заказчик уточняет у ИТ-службы. Не утверждай, что VPN уже настроен.
- Техническое сопровождение после передачи — **ИТ-служба компании**.
- Место размещения сервера, домен, внутренний DNS, TLS, сетевые правила, параметры резервирования и ресурсы сервера ещё не предоставлены. Отрази их в листе вопросов для ИТ, а не выдумывай.
- Не публикуй портал, БД, объектное хранилище или OCR с реальными данными в общедоступном интернете по умолчанию. Все пользовательские пути, файлы и внутренние сервисы должны соблюдать выбранный сетевой периметр.

Отсутствие production-домена/VPN не блокирует создание и проверку автономной локальной demo-среды. Production-доступ извне нельзя считать проверенным без реальной проверки ИТ.

## 3. Архитектура и повторяемая среда

Базовый стек для отдельного нового репозитория:

- React, TypeScript strict и Vite: только статический браузерный frontend, адаптивный UI и доступные компоненты; никаких SSR/BFF/API на JavaScript.
- Python 3.12+, Django LTS + Django REST Framework, REST `/api/v1`, OpenAPI; сервер — источник правил и прав. Владелец прямо запрещает JavaScript/TypeScript для backend, включая NestJS, Express, Node API, SSR/BFF и серверные маршруты Next.js. Node разрешён только как инструмент сборки frontend.
- PostgreSQL и Django ORM, версионируемые миграции, ограничения БД, индексы и транзакции. SQLite допустима только локально для разработки; её тесты не подтверждают работу production PostgreSQL.
- Зрелая поддерживаемая локальная система идентификации: для текущей реализации приняты Django auth + django-otp; отдельный Keycloak/OIDC допустим при обоснованной необходимости. **Пользователь входит по индивидуальному логину/паролю; корпоративный SSO не является условием запуска.** OIDC между приложением и собственным IdP допустим как внутреннее техническое решение.
- Сессия Python-сервера, HTTP-only cookies. Пароли, access/refresh tokens не хранятся в localStorage и не попадают в логи.
- Для выбранного одноузлового установочного комплекта — закрытый файловый том, недоступный Nginx/worker напрямую; выдача только через авторизованный Python API. S3-совместимое хранилище остаётся дополнительным инфраструктурным вариантом. Установка не должна требовать отдельного S3/IdP, если эквивалентные функции безопасно реализованы зрелыми компонентами; решение фиксируется ADR.
- PostgreSQL full-text/trigram или сопоставимый поиск, достаточный для указанного масштаба. Отдельный тяжёлый поисковый кластер без обоснования не нужен.
- Фоновая обработка файлов/OCR с сохраняемыми заданиями, повторными попытками и понятными статусами. Выбор конкретного движка подтвердить испытаниями на нужных языках.
- Обязательные карантин загрузок и локальная антивирусная проверка до публикации, скачивания, превью и OCR; отдельные статусы безопасности файла и извлечения текста. Будущая интеграция или заглушка не заменяют работающую защиту.
- Docker Compose для установки PostgreSQL, Python API/worker, закрытого тома, ClamAV и HTTPS-прокси; health/readiness probes; генерируемая приватная конфигурация без секретов в исходниках; закреплённые образы. Полный запуск должен проверяться фактически на совместимом стенде.
- Unit + integration/API + Playwright E2E, проверки доступности и отрицательные проверки прав.

Выбирай поддерживаемые совместимые версии на момент установки, проверяй официальную документацию и фиксируй lockfiles. Если выделенный репозиторий уже содержит эквивалентные рабочие решения, сначала оцени их и запиши ADR перед заменой. Самодельное хранение/проверку паролей не делай при наличии подходящего зрелого IdP.

## 4. Роли и границы самостоятельного редактирования

Используй три бизнес-роли: `EMPLOYEE`, `HR`, `ADMIN`. Роли проверяются на сервере. HR и ADMIN имеют обычные возможности чтения сотрудника.

| Операция | EMPLOYEE | HR | ADMIN |
| --- | --- | --- | --- |
| Читать опубликованные новости, документы и справочник | Да | Да | Да |
| Создавать, менять, архивировать/восстанавливать сотрудников | Нет | Да | Да |
| Импортировать и экспортировать кадровые данные | Нет | Да | Да |
| Управлять подразделениями и справочником офисов | Нет | Да | Да |
| Создавать, менять, публиковать новости/объявления | Нет | Да | Да |
| Загружать, менять документы, добавлять редакции | Нет | Да | Да |
| Удалять контент в корзину, восстанавливать, окончательно удалять | Нет | Да | Да |
| Создавать/блокировать аккаунты, сбрасывать пароли, назначать роли | Нет | Нет | Да |
| Системные настройки и техническое администрирование | Нет | Нет | Да |
| Читать/искать полную дату рождения с годом | Нет | Да | Да |
| Менять свой мобильный и его видимость | Да | Да | Да |
| Менять свои необязательные этаж и кабинет | Да | Да | Да |

В отличие от старого ТЗ **ADMIN управляет всеми разделами и кадровыми данными без необходимости второй роли HR**. HR ведёт не только сотрудников и структуру, но также документы, новости и объявления. Отдельная роль CONTENT_EDITOR не требуется.

Самостоятельное редактирование EMPLOYEE строго ограничено собственными `mobilePhone`, `mobileVisibility`, `floor`, `room`. ФИО, должность, подразделение, основной офис, руководитель, дата рождения, фото и роли не входят в этот список. HR/ADMIN управляют остальными кадровыми полями. Политику видимости рождения также ведут HR/ADMIN; собственный мобильный сотрудник может скрыть сам.

Фильтруй разрешённые поля на сервере, а не только в форме. Замена employeeId в запросе не позволяет менять коллегу. Не допускай обхода прав через импорт, прямой API, массовое назначение полей или архивирование. Неавторизованному — 401, авторизованному без полномочий — 403. Назначения ролей и критические действия журналируются. Нельзя назначить себе ADMIN/HR через профиль.

## 5. Учётные записи и жизненный цикл сотрудника

### 5.1. Вход и восстановление

- У каждого пользователя индивидуальные логин и пароль. Аккаунт создаёт **админ**; публичной самостоятельной регистрации нет.
- Админ выдаёт временный пароль; при первом входе обязательна его смена. Временный секрет показывается безопасно и не сохраняется в исходниках/логах/клиентском bundle.
- При забытом пароле админ выдаёт новый временный пароль. Самостоятельное восстановление через email и почтовый сервис для первого запуска не нужны.
- Дополнительное требование безопасности: для HR и ADMIN обязательна многофакторная аутентификация через выбранный IdP, например приложение-аутентификатор или поддерживаемый аппаратный фактор. Это дополнение к логину/паролю, а не возврат обязательного корпоративного SSO. Процедуру первичной настройки и восстановления фактора документировать для ИТ; сброс пароля не отключает MFA автоматически.
- Защита от перебора, безопасные ошибки входа, завершение сеансов и блокировка аккаунта обязательны. Корректно проверяй issuer/audience/expiration/signature, если используется OIDC.
- Bootstrap первого админа — защищённая документированная процедура, не публичная кнопка и не production demo-пароль.

### 5.2. Карточка отдельно от аккаунта

HR создаёт карточку сотрудника. Админ отдельно создаёт аккаунт и связывает его с карточкой по ID. До появления аккаунта сотрудник уже находится в справочнике, но не может войти. Сущности Employee и UserAccount раздельны; допускается карточка без аккаунта и временно не связанный аккаунт.

### 5.3. Архивирование и блокировка

При архивировании HR или админом карточка исчезает из общего справочника, история сохраняется, **связанный аккаунт автоматически блокируется**. Уже открытые сессии не должны сохранять доступ к защищённым операциям. Нельзя требовать отдельного ручного действия админа для первичной блокировки.

Если блокировка в IdP выполняется асинхронно, сервер портала немедленно запрещает доступ по своему состоянию аккаунта и повторяет синхронизацию надёжно; сбой фоновой задачи не оставляет рабочий вход. При восстановлении карточки не включай аккаунт незаметно: безопасный технический default — повторное включение админом, описанное в документации.

## 6. Карточка сотрудника, приватность и поиск

### 6.1. Поля

**Обязательны для сохранения:** ФИО, должность, подразделение, название основного офиса.

**Необязательны:** руководитель, внутренний номер, мобильный номер, дата рождения, фото, этаж, кабинет, служебный email. Не заставляй HR придумывать отсутствующие сведения. ФИО можно вводить понятным способом; не требуй обязательного отчества. Если из общего ФИО нельзя надёжно выделить части имени, не угадывай их молча.

У сотрудника **один основной офис**. Офис в UI — только название, выбранное из единого справочника. Несколько рабочих мест, адрес офиса и номер рабочего места не входят в эту версию. Этаж и кабинет могут добавить HR, админ или сам сотрудник; оба поля необязательны. Кабинет и этаж хранятся как текст при необходимости, например `301А`, `B-12`.

### 6.2. Видимость

- Заполненный **внутренний номер всегда виден** всем авторизованным сотрудникам. Переключателя скрытия нет даже у HR и админа. Если номер ещё не назначен, карточку можно сохранить без него.
- **Мобильный номер виден по умолчанию.** Его могут менять и скрывать HR, админ и сам владелец карточки.
- **День и месяц рождения видны по умолчанию.** HR/админ могут скрыть показ. Обычный сотрудник не получает год рождения или полную дату в API, HTML, SSR, экспорте и поисковых сниппетах.
- Полная дата рождения и поиск по ней доступны HR/админу. У скрытого дня рождения и мобильного нет поисковых совпадений/счётчиков/сниппетов для обычных пользователей.
- HR/админ сохраняют кадровый доступ к полям, скрытым от общего справочника.
- До загрузки фото — инициалы, без выдуманного портрета. Фото обрабатывается безопасно: resize/crop, удаление метаданных, лимиты.

### 6.3. Справочник

Поиск: ФИО, должность, офис, внутренний номер, видимый мобильный номер, разрешённая часть даты рождения. Для сотрудников дата ищется по дню/месяцу, для HR/админа доступна и полная дата. Поиск по доступным служебным контактам и подразделениям из исходного ТЗ сохраняется. Этаж/кабинет можно учитывать, если они заполнены и доступны, без превращения их в обязательные поля.

**Отдельное поле «За что отвечает» не вводить:** заказчик выбрал поиск по ФИО и должности вместо каталога вопросов/компетенций.

Карточки и компактный список, фильтры по подразделению и офису, пагинация, debounce, понятные пустые состояния. Офис отображается всегда, если карточка валидна; необязательные этаж/кабинет показываются только при заполнении. Удалённые из общего справочника сотрудники не попадают в обычный поиск.

Устойчивая ссылка `/employees/{id}`, переход к непосредственному руководителю и прямым подчинённым, переход в подразделение и к коллегам. Связи по ID, а не по тексту ФИО. Не путай офис с отслеживанием физического присутствия: такого мониторинга нет.

## 7. Номера сотрудников и контроль совпадений ФИО

У компании не предоставлены собственные постоянные табельные номера. Портал **автоматически присваивает уникальный постоянный номер** каждой новой карточке. Внутренний UUID и читаемый номер можно хранить раздельно. Формат вроде `TI-000001` — технический пример, не существующая нумерация компании. Номер не переиспользуется после архивирования.

При создании и импорте проверяй совпадение нормализованного ФИО: регистр букв, повторные/краевые пробелы. Возвращай предупреждение с найденными карточками и ссылками. Не объявляй совпадение имени доказательством одного и того же человека.

HR/админ могут:

1. Открыть существующую карточку и работать с ней.
2. Явно выбрать «Это другой сотрудник с таким же ФИО» и создать отдельную карточку с новым ID/номером.

Не сливай людей и не блокируй реальных тёзок. При повторной загрузке Excel стабильный номер используется для контролируемого обновления. Совпадение ФИО без номера — предупреждение и решение пользователя, а не молчаливый upsert.

## 8. HR-интерфейс, оргструктура и первоначальная загрузка

HR — основной ежедневный оператор данных. Для него особенно важен простой UX: найти → открыть → изменить → сохранить. Сотрудники также должны получать полноценный удобный интерфейс, а не административную таблицу.

- Общий пользовательский портал остаётся редакционным; HR-инструменты доступны в отдельном рабочем разделе и понятных контекстных действиях.
- Обязательных полей в форме только четыре из раздела 6. Необязательные сведения сгруппированы и не мешают сохранению.
- Подразделение, основной офис и руководитель выбираются из существующих записей; поддерживается поиск в списках.
- Валидация рядом с полем, сохранение после ответа сервера, понятное сообщение об успехе, защита от случайной потери несохранённого ввода.
- В HR-списке есть фильтр **«Без фотографии»** и удобная загрузка фото из карточки с обрезкой/предпросмотром.
- Структура — дерево без жёсткой глубины: компания, дирекция, департамент, управление, отдел, сектор и другие типы по справочнику. ФИО руководителей и названия узлов кликабельны.
- На странице подразделения: руководитель, дочерние узлы, сотрудники; переключатель «Только это подразделение / включая вложенные».
- HR и админ управляют подразделениями и офисами. Проверяй циклы дерева/подчинения, ссылочную целостность, перенос сотрудников при архивировании узла и переназначение руководителя.

**Первичная загрузка:** HR предоставляет список, импортирует Excel; фотографии добавляет отдельно через карточки. ZIP-фотоимпорт и извлечение встроенных фотографий из Excel не являются обязательными для первого запуска.

CSV/XLSX-импорт: шаблон, маппинг столбцов, предпросмотр, построчные ошибки, обязательные поля, проверка офисов/подразделений/руководителей, совпадения ФИО и номера, явное решение по конфликтам, отчёт результата. Никаких тихих перезаписей. После исправления/подтверждения выбранный пакет фиксируется транзакционно. Невалидные строки нельзя незаметно потерять или частично испортить данные.

Номера портала включаются в HR-выгрузку для последующих обновлений. Для ссылки на руководителя при повторном импорте используй стабильный номер/UUID; при их отсутствии предложи явное сопоставление или оставление необязательного поля пустым, не угадывай по имени. Экспорт полного кадрового реестра — только HR/админ, с аудитом.

## 9. Новости, объявления и главная

HR и админ создают, редактируют, публикуют, снимают с публикации, удаляют и восстанавливают новости и объявления. **Дополнительного процесса согласования нет.** Авторизованный обычный сотрудник читает, но не публикует.

Все публикации предназначены **всем сотрудникам**. Аудитории по офисам, подразделениям и руководству не нужны. Черновик не равен опубликованному материалу и обычным пользователям не показывается.

Главная:

1. Постоянная боковая навигация на широком экране и раскрываемое меню на узком; компактный верхний header с глобальным поиском, языком и профилем. Логотип только подтверждённый либо нейтральный текстовый знак.
2. Важные новости, которые HR/админ закрепляют вручную; редакционная подача с крупной главной публикацией и дополнительными карточками.
3. Свежие публикации автоматически по дате, не требующие ручного закрепления каждой новости.
4. Быстрые переходы к сотрудникам, оргструктуре, документам, News.
5. Дни рождения только с разрешённой видимостью, обновлённые документы и полезные материалы.

В разделе **News — все опубликованные новости и объявления**, по умолчанию сначала новые; закреплённые отмечены. Поиск, категории и пагинация. Удалённые материалы не показываются. Для пустого портала и малого числа публикаций предусмотрена аккуратная вёрстка без фиктивного наполнения.

Поля: заголовок, текст, краткое описание, обложка при наличии, категория, автор, даты публикации/обновления, закрепление, статус. Форматирование безопасно санитизируется; история изменений сохраняется. Расписание публикации/окончания из исходного ТЗ можно оставить необязательным, не усложняя основной путь.

**Нет кнопки «Ознакомился» и нет учёта подтверждения прочтения.** Нет слежения за глазами, прокруткой или попыток выдать открытие страницы за фактическое понимание текста.

Просмотры: при действительном открытии полной публикации учитывается уникальный авторизованный пользователь. Повторное открытие тем же аккаунтом не увеличивает число. Карточка в ленте, SSR-prefetch, загрузка превью или поискового результата не считаются просмотром. Уникальность обеспечивается сервером, например ограничением `(newsId, userAccountId)`.

Показывай только счётчик вида «37 просмотров». Поимённого списка читателей в интерфейсе нет. При изменении заголовка/текста той же публикации счётчик не обнуляется. Для первой поставки достаточно главной и раздела News; рассылки email/Telegram, push и дополнительные интеграции не входят в обязательный объём.

## 10. Документы: доступ, реквизиты и редакции

Документы ведут HR и админ. Они отвечают за загруженные сведения и при необходимости исправляют, заменяют либо удаляют их. **Не вводи обязательную проверку юристом, согласование, второго утверждающего или автоматическую юридическую экспертизу.** Не придумывай содержание, номера и даты актов.

Все опубликованные документы и их доступные предыдущие редакции видны **всем авторизованным сотрудникам**. Конфиденциальные документы ответственные не загружают в этот портал. ACL по отделам/должностям/группам не нужны. При этом файлы не публичные: без входа они недоступны, включая прямые ссылки и OCR-текст.

Реквизиты: название, категория, номер при наличии, дата документа, дата вступления в силу при наличии, описание, ответственное подразделение при наличии, версия/редакция, файл либо предоставленная официальная ссылка, статус публикации и даты изменений. Известные категории из исходного задания сохраняются: положения, регламенты, приказы, инструкции, шаблоны, политики, законодательство, прочее. Неизвестные реквизиты не заполняй догадками.

**Документ и его редакция — разные сущности.** HR/админ добавляют новую редакцию из существующей карточки, а не обязаны создавать несвязанную копию. Каждая редакция имеет постоянный ID/URL и отдельный неизменяемый объект файла. Не подменяй байты старого файла новыми по прежней ссылке.

При открытии старой редакции:

- Старый текст/файл доступен для чтения и скачивания.
- Заметная отметка **«Устаревшая редакция»**.
- Верхний баннер **«Есть более новая редакция документа»** и ссылка/кнопка **«Перейти к действующей редакции»**.
- История редакций с датами и переходами; из текущей редакции также можно открыть предыдущие.

Это требуемый сценарий навигации по редакциям; не нужно копировать дизайн или контент внешнего сайта. Статус действующей редакции задаётся ответственным HR/админом; портал не утверждает юридическую действительность материала от своего имени. Необязательная дата вступления в силу не должна незаметно менять опубликованную редакцию без явно описанной логики.

По умолчанию список и поиск показывают **текущие редакции**. В расширенном поиске есть «Искать также в предыдущих редакциях». Результат старой версии помечен и ведёт именно на найденную версию, с переходом к текущей.

## 11. Два режима поиска документов и OCR

### 11.1. Обычный поиск

Одна строка, поиск по названию и номеру документа. Быстрый путь без длинной формы. По умолчанию текущие опубликованные документы.

### 11.2. Расширенный поиск

Открывается по понятной кнопке, не загромождает базовый экран:

- Строка запроса по названию/номеру.
- Фильтры по **дате документа** и категории; понятные подписи полей, дата загрузки не подменяет дату документа.
- Опция **«Искать внутри файлов»**: извлечённый текст PDF, Word и распознанных сканов.
- Опция **«Искать также в предыдущих редакциях»**.
- Результаты с названием, номером/датой при наличии, отметкой версии, безопасным фрагментом найденного текста и ссылкой на нужную редакцию.

Глобальный поиск также возвращает сотрудников, подразделения, новости и документы с учётом приватности, статусов и пагинации. Полноценное расширенное управление документами находится в их разделе.

### 11.3. Извлечение и распознавание

Поиск внутри обязателен для текстовых PDF, Word и сканированных PDF. Для документов также принимаются сканы-изображения JPG/PNG/TIFF (многостраничный TIFF в пределах лимита страниц PDF) и распознаются картинки внутри DOCX; см. OCR_RESULTS.md. Для Word базовый обязательный формат — DOCX, как в исходном ТЗ; поддержку старого DOC либо реализуй безопасной проверенной конвертацией, либо явно укажи в UI допустимые форматы и ограничение. Нельзя обещать поддержку DOC без реализации/проверки.

Распознавание поддерживает **русский, узбекский на латинице, узбекский на кириллице и английский**, включая смешанные документы. Проверь специальные узбекские буквы и выбранные для интерфейса Ö/Ğ/Ş/Ç на тестовых образцах; отсутствие таких испытаний не называй подтверждённой поддержкой. OCR может ошибаться — не обещай безошибочный поиск по некачественным сканам.

Сначала файл проходит отдельный конвейер безопасности из раздела 16. Только после допуска файла фоновые задания извлекают существующий текст и запускают OCR для страниц, где требуется распознавание. Статусы OCR: ожидает / обрабатывается / готово / ошибка, при необходимости частичный результат. Это не статусы антивируса. Повторная попытка доступна HR/админу. Задания переживают перезапуск; одинаковый файл/версия не должен бесконтрольно порождать дубликаты заданий.

Пока идёт карантин/антивирусная проверка, загрузка видна только ответственным как ожидающая проверки и недоступна для скачивания, общего поиска, превью и OCR. После допуска по безопасности файл и поиск по реквизитам доступны, даже если OCR ещё обрабатывается. UI честно сообщает, что поиск внутри этой версии ещё не готов или завершился ошибкой. Ошибка OCR не должна блокировать весь портал и не должна скрываться от ответственных. HR/админ не могут обойти техническую проверку кнопкой «Всё равно опубликовать».

OCR и извлечение выполняются в согласованной внутренней среде, с лимитами страниц/размера/времени/памяти и изоляцией небезопасных файлов. Реальные документы не отправляются во внешний OCR/API по умолчанию. Оригиналы сохраняются; распознанный текст служит поисковым индексом и не подменяет официальный файл. Не переписывай исходные документы в новый алфавит и не переводи их автоматически.

Связывай извлечённый текст и индекс с конкретной версией. Индекс, сниппеты и кэши соблюдают публикацию, корзину, текущую/предыдущую редакцию и сетевую авторизацию. Защити обработчик от архивных бомб/вложений, чрезмерных ресурсов и опасных внешних обращений.

## 12. Корзина и окончательное удаление

Удаление новости, объявления или документа сначала перемещает материал в **корзину**, видимую HR и админу. Материал сразу исчезает из общего списка, главной, поиска и обычных файловых маршрутов. HR и админ могут восстановить или **окончательно удалить** его. Перед необратимым действием — явное подтверждение с названием материала; результат фиксируется в аудите.

Не вводи автоматический срок очистки, о котором не договорились: технический default — ручное окончательное удаление. Для документов учти все связанные редакции, файлы, задания OCR, индексы и временные ссылки; восстановление должно согласованно возвращать материал. Окончательное удаление данных из приложения не равно мгновенному удалению из резервных копий; сроки хранения копий документирует ИТ.

Сотрудников не подменяй этим сценарием: для них основной согласованный путь — **архивирование с автоматической блокировкой**, сохранением истории и номера. Не добавляй кнопку необратимого удаления сотрудника без отдельного требования.

## 13. Языки, алфавит и даты

Интерфейс по умолчанию — **узбекский с Ö/ö, Ğ/ğ, Ş/ş, Ç/ç вместо o‘, g‘, sh, ch**. Это явно выбранная заказчиком орфография интерфейса; не утверждай в документации, что её правовой статус/дата введения проверены. Русский — второй язык. При первом открытии узбекский, затем сохраняется выбор пользователя.

Весь интерфейс, формы, ошибки, кнопки, статусы, пустые состояния и письма, если они будут добавлены отдельно, переводятся через словари. Не делай только перевод меню при русских ошибках и HR-формах. Официальные имена, материалы и реквизиты сохраняются как введены/предоставлены, без принудительной транслитерации.

**Материалы можно публиковать на одном языке.** Перевод новости, объявления, названия/описания документа необязателен. При переключении интерфейса показывается доступный перевод; при его отсутствии — оригинал. Не требуй обязательного русского текста для публикации на узбекском и наоборот. Автоматический перевод и генерация официальных материалов не требуются.

Поиск учитывает варианты узбекского написания с o‘/g‘/sh/ch и Ö/Ğ/Ş/Ç, разные апострофы, регистр и пробелы; проверяй кириллицу/латиницу на репрезентативных примерах. Не обещай идеальную транслитерацию любых имён. Нормализация поисковых алиасов не изменяет исходный текст и не обходит правила видимости мобильного/даты рождения.

Часовой пояс отображения — `Asia/Tashkent`; временные отметки хранить нормализованно. Рождение — DATE с ограничением доступа, обычным пользователям только разрешённые день/месяц. Блок ближайших дней рождения корректно учитывает переход года и 29 февраля; порядок для 29 февраля в невисокосный год явно документируется и тестируется, без придуманной юридической нормы.

## 14. UI/UX для сотрудника, HR и админа

Современный редакционный портал, удобный справочник и библиотека, без постоянной тяжёлой ERP-панели для обычного сотрудника. Чёткая типографика, свободное пространство, понятные карточки, видимые действия. Официальный логотип/фото компании не придумывать.

Разделы: Главная, News, Сотрудники, Структура, Документы; дни рождения как доступный блок/раздел без перегрузки навигации. HR и админ видят понятный переход в управление и контекстные действия; обычный сотрудник — только разрешённое собственное редактирование.

Responsive от 320 px, desktop и мобильные устройства, доступность клавиатурой, видимый focus, корректные label/ошибки, контраст и практики WCAG 2.2 AA. Breadcrumb внутренних страниц, устойчивые URL, удобные назад/вперёд, loading/empty/error states, отсутствие исчезающих несохранённых изменений. Не скрывай необходимые действия на мобильном. Не называй соответствие WCAG доказанным без проверки.

Дополнительно проверь три реальные цепочки UX:

1. Сотрудник ищет коллегу с телефона, открывает карточку, звонит/копирует номер, переходит к руководителю.
2. HR импортирует список, видит ошибки/совпадение ФИО, сохраняет пакет, фильтрует «Без фотографии», добавляет фото и позже меняет должность в пару понятных шагов.
3. Сотрудник ищет слово в скане через расширенный поиск, открывает найденную старую редакцию и переходит к текущей.

## 16. Обязательная безопасность и допуск к эксплуатации

### 16.1. Проверяемая цель

Не обещай «абсолютную неуязвимость», «защиту от любого трояна/DDoS» или прохождение любого будущего пентеста. Устанавливай проверяемые меры и границы испытаний. Внутренняя сеть, доверие к HR и общий доступ сотрудников к документам не отменяют безопасность.

Целевой базис задания — **применимые требования OWASP ASVS 5.0.0 Level 2**, включая требования нижнего уровня; для высокорисковых функций применяются дополнительные меры ниже. Версия 5.0.0 проверена по официальной странице 01.11.2026. Веди матрицу ID требования → реализация → тест/доказательство → статус. N/A допустимо только с обоснованием. Это целевое требование, не уже достигнутая сертификация. Пентест не заменяет матрицу и автоматические проверки.

### 16.2. Аккаунты и полномочия

MFA обязательна для HR/ADMIN. Сессии — HTTP-only/Secure/SameSite, защищённый logout, CSRF, ограничения срока/бездействия, отзыв после блокировки/смены полномочий. Для назначения ролей, сброса фактора и окончательного удаления требуется свежая подтверждённая сессия; конкретную политику зафиксировать с ИТ. Подбор паролей/credential stuffing ограничивается, ошибки входа не раскрывают наличие аккаунта. Нет общих production-аккаунтов, дефолтных паролей и обхода MFA через восстановление.

Для EMPLOYEE также реализуй MFA. Базовая целевая схема L2 — многофакторный доступ всех пользователей: не объявляй выполнение v5.0.0-6.3.3 только по наличию второго фактора у админа. Если ИТ предлагает ослабление для обычных сотрудников, стандарт требует документированного обоснования и компенсирующих мер; решение проверяется независимо. Сам факт офисной сети/VPN не доказывает наличие второго фактора. Пока это не подтверждено, соответствие L2 не заявляется.

Проверяй роль, владельца записи и список разрешённых полей в API. Защита от IDOR/BOLA, повышения роли и массового присвоения полей обязательна, в том числе для self-service, импорта, медиа и прямых файловых маршрутов. Работающий токен не отменяет проверку активного состояния аккаунта.

### 16.3. Инъекции и обработка недоверенных данных

- SQL — параметризованные запросы; динамические сортировки/поля только из серверного списка. ORM не оправдывает конкатенацию raw SQL. Рабочая роль БД без superuser/DDL; миграции выполняются отдельно.
- Rich text, названия, OCR-фрагменты и импортированные данные выводятся с контекстным экранированием; строгая санитизация и CSP. Не исполнять шаблоны/HTML/JavaScript из контента.
- OCR/конвертер вызываются без shell-конкатенации: фиксированная программа, разделённые аргументы, проверенные параметры. Имена файлов не становятся командами.
- Запретить небезопасную десериализацию, XXE/DTD, traversal/Zip Slip; ограничить регулярные выражения и длины ввода. При CSV/XLSX-экспорте нейтрализовать формулы в недоверенных текстовых ячейках; импорт не исполняет формулы/макросы.
- Не скачивать произвольный введённый URL сервером. Если fetching действительно нужен, применить allowlist назначения и сетевые ограничения с учётом redirects/DNS/IPv6, запретить metadata/loopback и другие несогласованные внутренние адреса. Ссылка на документ сама по себе не требует server-side fetching.

### 16.4. Файлы: карантин до любого использования

Все загружаемые документы, Excel/CSV, фото и обложки считаются недоверенными, даже от HR/админа. Обязательная последовательность: **загрузка в закрытый карантин → проверка типа/структуры и лимитов → антивирус → допуск → безопасное превью/извлечение/OCR → публикация**. Проверки структуры также выполняются изолированно.

Проверять фактический тип/сигнатуру и структуру, а не только расширение/MIME от браузера. Разрешать только нужные форматы; запретить исполняемые файлы, скрипты, макросодержащие Office-файлы и произвольные архивы. DOCX/XLSX проверять с лимитами распакованного размера/вложений. Шифрованные/непроверяемые файлы отклонять с понятным объяснением. Legacy DOC принимается только при отдельно реализованной столь же защищённой цепочке; иначе явно отклоняется.

Использовать работающий локальный антивирус с обновляемыми базами. Ошибка, timeout, превышение лимита проверки или недоступность антивируса — **не допуск**, файл остаётся заблокированным. Зафиксировать порог свежести баз. Нет обхода для HR/ADMIN. Результат «ничего не обнаружено» не означает доказанную безвредность.

Ключи объектов генерируются сервером. Никакого исполнения из каталога загрузок или открытого bucket. PDF с активным содержимым/вложенными исполняемыми объектами отклоняется либо обрабатывается безопасной проверенной цепочкой. Для CDR/превью создаётся отдельный производный объект; оригинал и цифровая подпись не подменяются. Подозрительный оригинал не раздаётся под видом безопасного превью. Безопасность проверяется и для старых редакций.

### 16.5. Изоляция обработки и сервера

OCR/парсеры/превью — непривилегированный worker с ограничениями CPU/RAM/процессов/времени/страниц/пикселей/диска. У него нет shell-администрирования, Docker socket, секретов БД или доступа ко всем оригиналам; только необходимые конкретному заданию объекты через ограниченный интерфейс/краткоживущий доступ. Произвольный исходящий трафик запрещён; обновления баз антивируса идут по отдельному контролируемому пути.

Контейнеры без privileged/root и лишних capabilities, read-only filesystem где возможно, ограниченные tmp-каталоги, seccomp/AppArmor либо эквивалент, обновляемый host. Контейнеризация не является гарантией изоляции. БД, storage, IdP-admin и worker не имеют общедоступных портов.

### 16.6. DoS/DDoS: приложение и сеть

В приложении: лимиты по аккаунту и IP на вход, запросы, поиск, upload/download, import и OCR; ограничение длины запроса, размера страницы/файла, распаковки, query timeouts, числа соединений и фоновой очереди. Ответы 429/503 при перегрузке, обратное давление и ограничение конкурентного OCR. Одна тяжёлая загрузка не должна отбирать все ресурсы у чтения портала. Общий офисный IP не должен приводить к блокировке всех 150 сотрудников. Forwarded-заголовкам доверять только от настроенного proxy.

В инфраструктуре: firewall, сетевое разделение, закрытый origin и надёжный reverse proxy; WAF при внедрении настраивается/проверяется и не заменяет исправление кода. Проверить IPv4/IPv6, storage и прямые адреса, исключить обход VPN через альтернативный маршрут.

**Объёмный DDoS способен перегрузить интернет-канал/VPN-шлюз ещё до приложения.** ИТ совместно с провайдером определяет фильтрацию выше по сети, защиту шлюза, ёмкость и порядок реакции. Ни VPN, ни локальный rate limiter не гарантируют устойчивость к любому объёму атаки. Согласовать измеримый профиль нагрузки/атак, лимиты и целевое восстановление; пока они не заданы, DDoS-устойчивость не считать проверенной. Число 150 — пользователи, а не подтверждённая одновременная нагрузка.

### 16.7. Обнаружение, обновления и восстановление

Нужны защищённый audit, оповещения ИТ о попытках обхода прав, всплесках входа, заражённых/непроверенных файлах, сбоях антивируса, росте очереди/диска/ошибок. Не логировать пароли/токены и лишние кадровые данные. Разделить права приложения, БД, файлов и резервирования. ИТ документирует действия при компрометации аккаунта/сервера: изоляция, отзыв сессий, смена секретов, сохранение доказательств, восстановление.

CI: SAST, SCA, secret scanning, проверка контейнеров/IaC, SBOM и воспроизводимая сборка. Версии/базы обновляются; новая находка после запуска требует оценки и исправления. Резервные копии шифруются с отдельным доступом; хотя бы одна защищена от перезаписи учётной записью приложения. Restore БД, оригиналов/редакций и IdP фактически проверяется; RPO/RTO и сроки хранения определяются с ИТ. Юридическое соответствие отдельно не объявлять доказанным.

### 16.8. Условия допуска после проверки

До работы с реальными данными — независимый пентест production-подобной среды: web, API, IdP/сессии, все роли, self-service, импорт, загрузки/превью/OCR, старые редакции, сеть и конфигурация. Для VPN/шлюза привлекается ответственный инфраструктуры. Автоматический сканер не заменяет ручную проверку логики/прав.

**Запуск запрещён при незакрытых подтверждённых Critical/High**, обходе авторизации/MFA/карантина, удалённом исполнении кода или доступной цепочке средних находок с критическим последствием. Эта жёсткость — критерий проекта, а не обещание стандарта. Остальные находки документируются с ответственным и сроком; спорные false positives проверяются и обосновываются, а не скрываются.

После исправлений обязателен повторный тест. Сохранять commit/build digest, конфигурацию/версии, scope, дату, методики, результаты и ограничения отчёта. Контролируемые нагрузочные/DoS-испытания проводить в согласованной тестовой среде с профилем и условиями остановки, не создавать реальную распределённую атаку. Показать восстановление после отказа/перегрузки. Будущий отчёт не гарантирует безопасность навсегда.

## 18. Обязательные фактически выполненные проверки

Сначала напиши и реально запусти проверки, затем отражай результаты. Минимальная приёмка:

1. Clean install, lint, typecheck, build; миграции и запуск по README без правок исходников.
2. Гость не читает портал, API, файлы и извлечённый текст. Все три роли входят по индивидуальным логину/паролю; временный пароль требует смены.
3. EMPLOYEE не создаёт/меняет чужие карточки и не публикует через прямой API. HR и ADMIN реально создают и меняют сотрудников/контент. HR не создаёт аккаунты и не назначает роли.
4. Своя смена мобильного/видимости/этажа/кабинета разрешена; подстановка чужого ID и попытка изменить ФИО/офис/роль запрещены.
5. Заполненный внутренний номер виден всегда, скрыть через UI/API нельзя. Мобильный и рождение видны по умолчанию; после скрытия не раскрываются через обычный поиск, JSON, SSR, счётчик и сниппет.
6. Обычный пользователь видит/ищет только разрешённые день/месяц рождения, год не попадает в его payload. HR/ADMIN могут работать с полной датой.
7. Поиск находит ФИО, должность, офис, внутренний/видимый мобильный, разрешённую дату; кириллица/латиница и выбранные узбекские варианты проверены примерами.
8. Карточка существует без аккаунта; админ связывает их. Архивирование HR автоматически блокирует вход и существующий доступ; перезапуск/сбой синхронизации не возвращает доступ.
9. Обязательные поля только согласованные; пустые фото/контакты/этаж/кабинет не ломают UI. Один основной офис, поле номера рабочего места отсутствует.
10. Постоянные номера уникальны, не переиспользуются; одинаковое ФИО вызывает предупреждение/ссылку, подтверждённый тёзка создаётся отдельно. Повторный импорт с номером не создаёт дубликат.
11. Excel/CSV preview, ошибки/конфликты и явный commit работают; нет тихих перезаписей. Фильтр «Без фотографии» и загрузка фото после импорта проверены.
12. Руководитель/подразделение кликабельны; прямые подчинённые, дерево и включение потомков корректны, циклы запрещены.
13. HR/ADMIN публикуют без дополнительного согласования. Все сотрудники видят опубликованные материалы всех офисов; черновики/корзина не видны.
14. На главной важные закрепляются вручную, новые идут по дате; News содержит все опубликованные новости/объявления.
15. Уникальные просмотры: одно полное открытие — один просмотр; повтор/карточка/prefetch не добавляют. Нет кнопки ознакомления, поимённого списка и заявления о фактическом прочтении.
16. Обычный поиск документов работает по названию/номеру; расширенный — по дате/категории и с опцией поиска внутри.
17. Реальное извлечение PDF/DOCX и OCR сканированного PDF проходит на русском, узбекском латиницей/кириллицей, английском и смешанных страницах. Проверены очередь, ошибка, повтор и перезапуск. Отсутствие подходящего движка/модели языка — явный блокер, не «готово».
18. Новая редакция сохраняет старый файл/URL. Старую можно читать/скачивать; баннер ведёт к действующей. Поиск по умолчанию текущий, режим истории находит помеченную старую версию.
19. HR/ADMIN удаляют в корзину, восстанавливают и окончательно удаляют с подтверждением. EMPLOYEE не может этого сделать. Индексы/файлы/задания согласованы со статусом.
20. Узбекский интерфейс по умолчанию с Ö/Ğ/Ş/Ç, русский переключается и запоминается. Материал на одном языке публикуется без обязательного перевода, fallback показывает оригинал.
21. Desktop/mobile, клавиатурная навигация и ключевые цепочки сотрудника/HR проверены в браузере; снимки не подменяют функциональные тесты.
22. Данные переживают перезапуск; backup/restore выполнен на тестовой среде. Замеры на ~150 синтетических пользователях/карточках и представительном архиве отражены с параметрами, без вымышленных SLA.
23. Проверены обязательная MFA HR/ADMIN, реализация выбранной MFA-схемы остальных пользователей согласно v5.0.0-6.3.3, восстановление без обхода и отзыв уже открытых сессий после блокировки/смены прав. Любое ослабление для EMPLOYEE имеет проверенное обоснование и компенсирующие меры, иначе соответствие L2 не заявляется.
24. Файл в карантине не публикуется/не скачивается/не индексируется и не попадает в OCR даже по прямому URL. После допуска файл доступен при ещё работающем OCR; безопасность и OCR — независимые статусы.
25. Без настоящих вирусов проверены цепочка антивируса безопасным EICAR-образцом в изолированной среде, подмена расширения, контролируемые тесты лимитов распаковки/вложений/пикселей. Остановка scanner, старые базы, timeout или превышение лимита не дают статус допуска. Тест одного EICAR не доказывает обнаружение всех троянов.
26. Проверены SQL/command injection, stored/reflected XSS, SSRF/XXE, traversal/Zip Slip, CSV formula injection, CSRF, небезопасные поля self-service и недопустимые роли. Для каждого — отрицательная проверка и доказательство результата.
27. Проверены network egress/права worker, отсутствие Docker socket/лишних секретов и публичных внутренних сервисов. Компрометация одного задания не должна автоматически давать доступ к БД/всему storage.
28. Выполнены согласованные ограниченные нагрузочные/DoS-испытания и проверка восстановления. Инфраструктурная DDoS-защита канала/VPN подтверждается отдельными сведениями ИТ/провайдера; одни HTTP-тесты её не доказывают.
29. Матрица применимых ASVS L2 требований заполнена доказательствами; есть результаты CI-проверок и независимого пентеста. Исправления подтверждены ретестом, критические/высокие и опасные цепочки не оставлены открытыми.

Для каждой проверки укажи команду, окружение, результат, дату и ссылки на тесты/отчёты. Если Docker/браузер/движок/OCR-модели недоступны, выполни возможное и явно отдели незапущенные сценарии. Нельзя считать mock/OCR-заглушку проверкой реальной обработки файла.

## 19. Документация, этапы и передача ИТ

Создай README, CHANGELOG, .env.example и docs:

- architecture.md — компоненты, вход по логину/паролю, границы доверия, обработка файлов.
- permissions-matrix.md — три роли, разрешённые self-service поля, положительные и отрицательные API-проверки.
- data-model.md — сущности, версии, номера, приватность, инварианты.
- search-and-ocr.md — обычный/расширенный поиск, языки, статусы/повторы, реальные испытания и ограничения.
- deployment.md — dev/staging/prod, сеть/VPN, TLS, domain/env, миграции, обновление и rollback.
- operations.md — резервирование/восстановление, IdP, storage, OCR, мониторинг, блокировки.
- security.md — реализованные меры, угрозы, ограничения, непроверенные юридические/организационные требования.
- threat-model.md, asvs-matrix.md, security-test-results.md — границы доверия, трассируемые проверки, независимый пентест/ретест и статус допуска; не фиктивные отчёты.
- test-plan.md — команды и фактические результаты.
- IMPLEMENTATION_STATUS.md — выполненное, блокеры и следующие команды для продолжения.

Этапы исполнения:

**A. Аудит и каркас:** v3 gap-analysis, репозиторий, сборка, БД/миграции, Compose, IdP/storage, healthchecks.

**B. Вход и справочник:** роли, аккаунты отдельно от сотрудников, HR/ADMIN CRUD, обязательные поля/приватность/self-service, структура, номера/дубликаты, Excel/фото, авто-блокировка, audit.

**C. Контент:** главная/News, просмотры, документы/неизменяемые редакции/корзина, обычный/расширенный поиск, настоящее извлечение/OCR, RU/UZ UI.

**D. Проверка:** API/RBAC/IDOR/privacy, реальные файлы и языки OCR, desktop/mobile, миграции/backup/restore, исправление ошибок.

Этап D также включает реализованный карантин/антивирус, MFA, CI security checks, матрицу ASVS, контролируемые тесты перегрузки и подготовку независимого пентеста. Если независимый тест ещё не проведён, честный статус — «Реализовано/проверено разработчиком; допуск по безопасности не подтверждён», а не production-ready.

**E. Передача:** повторяемый запуск, фактическая таблица требований, инструкции ИТ и список ещё не полученных внешних параметров.

После этапа сообщай: изменённые файлы → рабочие сценарии → запущенные команды/результаты → не проверено/блокеры → следующий шаг. Делай логичные коммиты, обновляй статус и CHANGELOG. При исчерпании контекста сохрани безопасный завершённый результат и handover с точными следующими командами, не объявляй незавершённый этап готовым.

Финал: таблица «Требование → Где реализовано → Как проверено → Статус», реальные команды запуска, путь к Swagger и тестам, инструкция первого входа, ограничения, передача ИТ. Не выдумывай репозиторий, сервер, адрес, секреты, показатели или результаты тестов.

## Уточнение владельца: серверный язык

Backend запрещено писать на JavaScript либо TypeScript. Выбран Python + Django/DRF. Frontend работает в браузере и отображает данные/решения backend; проверки прав и бизнес-правила выполняются сервером. Выбор языка не является доказательством стабильности или безопасности. Требования к тестам, восстановлению, карантину, нагрузке и независимому пентесту сохраняются. Начальная реализация поставляется отдельно с фактическим статусом, без утверждения о готовности production.


## Передача установочного комплекта ИТ-службе

Владелец требует довести портал до состояния установки на сервер и подключения к корпоративному VPN без дописывания кода. Сервер уже есть, но его ОС владельцу неизвестна. Подготовлен профиль Linux x86_64 сервер/VM с Docker Engine/Compose. На Windows Server ИТ может выделить Linux VM; не предполагай замену действующей ОС. Нужны автоматическая генерация секретов, настройка по сетевым параметрам/сертификату, миграции, реальная проверка AV/OCR/прав, первая зашифрованная копия, восстановление, обновление и расписание контроля.

Не выдавай синтаксическую проверку Compose за сборку/запуск контейнеров, SQLite за PostgreSQL, протокольную имитацию AV за настоящий ClamAV, тесты криптографии за восстановление production-БД. Отсутствующие сведения о DNS/VPN/TLS/сервере/копиях заполняет ИТ. Полный запуск и восстановление на стенде, браузерная/нагрузочная приёмка и независимый пентест/ретест остаются обязательными условиями допуска реальных данных. Текущий исходный комплект маркируется release candidate до подтверждения этих условий.
