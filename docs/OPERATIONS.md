# Эксплуатация и восстановление

Работать из постоянного каталога релиза под одним системным пользователем (в примерах root через sudo). Сохранить `.deploy` при смене пакета. Не пересоздавать секреты и не выполнять `docker compose down -v`: это удаляет данные.

## Команды

| Команда | Назначение |
|---|---|
| `sudo python3 portalctl doctor` | Совместимость, ресурсы, пакет, конфигурация |
| `sudo python3 portalctl status` | Контейнеры, последний технический отчёт |
| `sudo python3 portalctl check` | БД/миграции/роль, storage, AV, worker/модели/изоляция, HTTPS и свежая копия |
| `sudo python3 portalctl check --pipeline --files` | Дополнительно настоящая AV/OCR-цепочка и SHA-256 допущенных файлов |
| `sudo python3 portalctl backup` | Согласованная зашифрованная копия БД и файлов |
| `sudo python3 portalctl verify-backup /path/snapshot` | Manifest/HMAC, размеры/хеши и теги AES-GCM обоих потоков |
| `sudo python3 portalctl update` | Сборка заранее, копия, остановка, миграции, запуск и проверки |
| `sudo python3 portalctl schedule --enable` | Системные ежедневная копия и ежеминутная проверка |

## Копии

На время согласованного снимка кратко останавливаются вход, API и worker; задания безопасно переводятся в очередь до pg_dump. БД и private-files архивируются потоками и шифруются AES-256-GCM. На диске не создаётся промежуточный открытый SQL/tar. Сервисы-инструменты имеют `logging: none`, чтобы Docker не сохранял открытый tar/дешифрованный поток в журнал. Ключ поступает инструменту через stdin, не аргументы/переменные среды.

Manifest подписывается HMAC, содержит хеши/размеры шифротекстов и ID релиза. Полные теги проверяются до фиксации копии и до изменения данных при восстановлении. Неполные копии остаются `.partial-*` и не считаются успешными. Завершение пишет `.deploy/last-backup.json`; отсутствие недавней копии обнаруживает health check.

По умолчанию полные аутентифицированные копии хранятся 14 дней, минимум три последних сохраняются. Чужие каталоги, копии с другим ключом и повреждённые объекты автоматически не удаляются. Контролировать объём `.partial-*`/невалидных копий, свободное место и ошибки backup service. Реальное RPO/RTO утверждает ИТ после испытания; расписание daily — стартовая настройка, не обещание SLA. Плановая остановка нужна для согласованности простой одноузловой схемы.

Хранить копии отдельно от сервера, желательно NAS/другой носитель; recovery key `.deploy/keys/backup.key` — отдельно в защищённом хранилище ИТ. Совместная потеря диска с данными/копиями/ключом не устраняется программой. Без ключа GCM копии восстановить нельзя.

## Восстановление

На новом совместимом сервере: распаковать соответствующий пакет, настроить DNS/TLS/сети, выполнить configure/install, получить API/worker-образы того релиза, который указан в manifest снимка. Старые проверенные образы и соответствующий исходный ZIP нужно сохранять вместе с планом восстановления; не применять автоматический image prune.

```bash
sudo python3 portalctl restore /mnt/backup/toshkent-portal/SNAPSHOT \
  --confirm portal.company.internal --replace \
  --key-file /secure-vault/original-backup.key
```

`--key-file` нужен при восстановлении копии другого ключа на новом хосте. Текущий ключ новой установки не перезаписывается. Имя в `--confirm` должно точно совпасть с настроенным; без `--replace` данные не заменяются. Сначала проверяются manifest/оба GCM-тега и наличие образов. Затем делается страховочная копия текущего состояния, останавливаются сервисы, восстанавливаются БД одной транзакцией и файлы с запретом обхода путей/ссылок, возвращаются runtime-права, отзываются все сеансы, задания возвращаются в очередь. После проверки байтов/готовности создаётся копия восстановленного состояния.

При ошибке восстановления сервисы остаются остановленными; при неудачной проверке после повторного запуска доступ снова закрывается; использовать страховочный снимок и отчёт. Базы должны быть доступны для страховочного pg_dump. При физически повреждённой БД восстанавливать на новой исправной установке, не уничтожать старый volume без отдельного плана ИТ. Восстановление PostgreSQL/контейнеров здесь не выполнялось; локальные round-trip тесты относятся к криптографии/архиву, не к PostgreSQL.

## Обновления и контроль

Заменить каталог релиза новым **проверенным** пакетом целиком, перенеся в него `.deploy` (не распаковывать поверх: оставшиеся старые файлы `apps/web`/`frontend-dist` не пройдут проверку), затем update. Порядок: [server-handoff/handout.md](../server-handoff/handout.md), раздел 10. В начале собираются новые образы, старые теги сохраняются; затем создаётся предобновленческая копия. Смена major PostgreSQL автоматически запрещена. При ошибке после миграции сервисы останавливаются; один откат образа не откатывает схему. Восстановить предобновленческий снимок вместе с соответствующим образом.

Systemd timers: `toshkent-portal-backup.timer` и `toshkent-portal-health.timer`. Подключить их ошибки/журнал к существующему мониторингу ИТ. При плановой операции check сообщает `planned-maintenance`, а не ложное «готово». Уведомления сотрудникам/почтовый сервис автоматически не настраиваются.

Контролировать 5xx/429 и задержку, очередь/ошибки worker, ресурсные лимиты, свободное место, срок TLS, свежесть ClamAV, копии, неудачные входы/MFA и изменения ролей. PostgreSQL не пишет параметры запросов; Nginx пишет агрегаты без URI/полей пользователя. Не включать verbose SQL/access logging с персональными значениями. Для продления TLS ИТ обновляет соответствующие `.deploy/tls` файлы с прежними правами, проверяет `nginx -t`, выполняет `nginx -s reload` через compose и повторяет check. Не передавать приватный ключ в чат/репозиторий.

## Изменения восстановления rc.4

Decrypt использует временную копию ciphertext и проверяет полный GCM-тег до выдачи открытого потока. Для контейнерных инструментов TMPDIR указывает на backup-work; на диске нет промежуточного открытого SQL/tar. Unpack сначала заполняет закрытый staging внутри private-files, затем заменяет дерево с откатом. При ошибке отката staging сохраняется и дальнейший backup блокируется. Не удалять его автоматически; см. RESTORE_ACCEPTANCE.md. Страховочный снимок при restore не возобновляет API/worker/proxy между снимком и заменой данных.
