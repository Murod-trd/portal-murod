# PostgreSQL 17: переход Debian → Alpine

Новая установка использует закреплённый PostgreSQL 17 / Alpine 3.24. Меняется libc и набор системных collation. Старый каталог данных Debian нельзя подключать к новому образу. `portalctl update` отказывается от изменения major-версии или варианта ОС до любых сборок, остановок и изменений конфигурации.

Для уже установленной Debian-версии нужен отдельный перенос через `pg_dump` / `pg_restore` в **новый** PostgreSQL-том. Сохраните прежние образы, конфигурацию, тома и recovery-ключ. Не удаляйте их до приёмки новой установки. Не используйте `docker compose down -v` для переноса.

Порядок для ИТ:

1. Остановить запись через proxy/API/worker. Создать и проверить аутентифицированную резервную копию БД и файлов штатными инструментами; ключ хранить отдельно.
2. Подготовить отдельную установку с другим Compose project, новыми томами и закрытым адресом. Создать штатные owner/app-роли и расширение `pg_trgm`. Прежний том не монтировать.
3. Проверить полный GCM-тег и HMAC до выдачи plaintext. Восстановить логический dump одной транзакцией и файлы через проверяемое промежуточное дерево. Применить владельцев и ограниченные app-права; пересоздать индексы. Ошибки collation или уникальности не игнорировать.
4. До открытия записи сравнить `recovery_inventory` с остановленным источником и выполнить `verify_private_files`. Проверить обе редакции документов, оригинальные байты, историю, нумерацию, импорт, аккаунты, пароль/MFA. Отозвать прежние сеансы через `recover_processing --workers-stopped --invalidate-sessions`.
5. Проверить HTTPS, доступ с офисных/VPN-сетей, полный AV/OCR и резервное копирование новой установки. Переключать корпоративный адрес только после этих проверок. При ошибке сохранить старые байты и вернуть прежнюю установку; не допускать одновременной записи в обе копии.

Это порядок отдельной миграции для квалифицированного оператора, не автоматический `update` поверх существующего тома. Политика обновления не допускает даже перехода Alpine 3.24 → 3.25 без отдельной проверки.
