# ADR 001 — весь бэкенд на Python

01.11.2026. Решение основано на прямом запрете заказчика писать бэкенд на JavaScript. Запрет включает TypeScript, компилируемый в JavaScript. Начатые серверные файлы NestJS удалены.

Бэкенд: Python, поддерживаемая LTS-ветка Django 5.2, Django REST Framework. Пароли/сессии — стандартный Django auth, MFA — django-otp, ORM и транзакции — Django. Все бизнес-правила, приватность, поиск, импорт, версии, просмотры, обработка файлов и выдача разрешений — на сервере Python.

Фронтенд: React/TypeScript, сборка в статические HTML/CSS/JS через Vite. Node используется только как инструмент сборки фронтенда в CI или на машине разработчика; на сервере Node/npm не запускаются ([ADR 004](004-no-node-on-server.md)). Нет Next.js SSR, BFF, API routes, Node-сервера, backend-кода JS/TS или клиентского источника прав.

Production требует PostgreSQL; локальная SQLite разрешена только для автономной разработки и явно не выдаётся за испытание PostgreSQL. Docker/ClamAV в текущей среде пока отсутствуют. Это ограничения проверки, не основания отключать карантин.

Миграции и доменные операции используют ORM. Запросы к пользовательским данным не строятся конкатенацией SQL. Графовые/импортные записи сериализуются транзакционно: advisory lock в PostgreSQL, ранняя блокирующая запись в SQLite. Требуется проверка обеих конфигураций, прежде чем заявлять поддержку.

Сам по себе выбор Python не гарантирует надёжность: обязательны фактические проверки, восстановление, мониторинг и независимый пентест. Keycloak/SSO не входят в обязательную текущую схему индивидуальных логинов/паролей.
